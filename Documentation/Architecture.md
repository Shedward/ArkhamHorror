# Архитектура и стек DistrictDeck

DistrictDeck запускает готовые сюжетные кампании на Mac и iPad. Автор задаёт содержание и сочетает поддерживаемые игровые механики в архиве. Игрок принимает решения, а одно Swift-ядро исполняет правила в приложении и в автоматическом тесте. Ниже зафиксированы решения для первой версии. В репозитории есть каркас приложения, UI-пакет со стартовым экраном и исходники тестовой кампании. [Формат кампании](CampaignFormat.md) [Принципы проекта](Principles.md) · [Базовые правила](GameRules.md)

## Согласованный стек

| Часть | Решение для первой версии |
| --- | --- |
| Сборка | Xcode 27.2, Swift 6, локальные пакеты Swift Package Manager. Общий таргет приложения в `DistrictDeck.xcworkspace`, конфигурация проекта в `project.xcproj`. Минимумы — macOS 15 и iPadOS 18. [Конфигурация сборки](../DistrictDeck.xcodeproj/project.xcproj) |
| Интерфейс | SwiftUI для библиотеки, карточек, панелей и журнала. Игровое поле — сцена RealityKit внутри `RealityView` с `OrthographicCameraComponent`. Ракурс для первой версии фиксирован. Карту можно двигать и приближать. Движение фишек и эффекты правил оцениваем на «Последнем поезде». [Сравнение стеков и причины выбора](UIStacks.md) |
| Кампания | Файл `.districtdeck` — обычный ZIP с исходными YAML-файлами и всеми ресурсами приключения. YAML удобно читать и обсуждать при ревью кампании. CLI `CampaignTool` проверяет авторскую папку и собирает архив. Приложение использует тот же валидатор при установке. |
| Сохранение | Один YAML-файл на прохождение. Вместе хранятся снимок партии, журнал и ссылка на точную установленную копию кампании. Форматом записи владеет `SavedGames`. Такой файл можно прочитать при отладке и использовать как фиксированную позицию в тесте. |

## Слои и границы пакетов

Зависимости идут от приложений к продуктам и общим инструментам. `Apps` собирает приложения, CLI и лабы. `Domain` содержит продуктовую логику. Его пакеты могут использовать `Core` и явно зависеть друг от друга без циклов. В `Core` выделяем общие технические инструменты по мере появления потребителей.

У пакета одна понятная задача, свой `Package.swift`, небольшой публичный API и при необходимости собственные тесты. Новую функциональность сначала помещаем в пакет-потребитель. Отдельный пакет появляется, когда подсистему удобнее развивать самостоятельно или когда она нужна другому потребителю. Например, поиск пути по графу может начаться рядом с правилами перемещения в `GameEngine`. Если граф понадобится отдельной лабе, алгоритм можно выделить, а стоимость перемещения за ход оставить в правилах партии.

| Компонент | За что отвечает |
| --- | --- |
| `Domain / GameEngine` | Владеет игровой моделью кампании, текущим состоянием партии и правилами. Принимает решение игрока, определяет допустимые действия и выдаёт их последствия по порядку. Движок поставляет базовый цикл хода и единый каталог типизированных команд. При компиляции скрипта из каталога выбираются команды, для которых место запуска гарантирует нужные данные. Расширение набора разбираем на конкретной игровой механике. |
| `Domain / CampaignArchive` | Читает и проверяет структуру файлов, ссылки, ресурсы и правила, затем строит модель кампании в типах `GameEngine`. Отвечает за упаковку и установку кампании в локальную библиотеку. Формат архива может меняться независимо от исполнения правил. |
| `Domain / SavedGames` | Реализует дисковое хранилище и отвечает за атомарную замену файла при автосохранении. Зависимость в манифесте — `SavedGames → GameEngine`. Движок определяет снимок и контракт сохранения и восстановления. Во время партии он обращается к хранилищу через этот контракт. |
| `Apps / DistrictDeck` и `DistrictDeckUI` | Приложение соединяет загрузчик, движок и хранилище. UI передаёт решения игрока и показывает состояние. Сцена отвечает за камеру и анимации. Маршрут, стоимость хода и результат встречи определяет движок. Все кампании используют общие экраны приложения. |
| `Apps / CampaignTool` | Даёт агенту команду сборки из папки с YAML и ресурсами. Проверки и упаковку выполняет `CampaignArchive`. При ошибке автор получает диагностику с указанием файла и проблемного элемента. |

Слои описывают ответственность. Физическое дерево первого этапа предлагается таким:

```text
Core/
Domain/
  GameEngine/
  CampaignArchive/
  SavedGames/
Apps/
  DistrictDeck/
  DistrictDeckUI/
  CampaignTool/
  Labs/
Fixtures/
  Campaigns/
```

Точка входа уже находится в `Apps/DistrictDeck/`. Действующий UI-пакет лежит в `Packages/App/DistrictDeckUI/`, а workspace обнаруживает локальные пакеты внутри `Packages/`. Размещение пакетов непосредственно от корня — предложение для будущего переноса. Исходники тестовых кампаний храним в репозитории, игровые кампании готовим отдельно. В `Reference/` доступны примеры встреч и тесты графа и колод из прежнего прототипа. [Текущее устройство workspace](../DistrictDeck.xcworkspace/contents.xcworkspacedata) · [Обзор прототипа](../Reference/docs/architecture-review.md)

## От архива до продолжения партии

1. **Сборка.** Агент передаёт папку в `CampaignTool`. После проверки утилита упаковывает проверенные YAML-файлы и ресурсы в ZIP. Файлы ресурсов лежат в корневой папке `resources/` с подпапками по назначению. Ссылка `"@board/train.png"` в любом YAML разрешается в `resources/board/train.png`. Сборщик и приложение при открытии архива проверяют каждую такую ссылку: путь остаётся внутри `resources/` и указывает на существующий файл. Ошибка указывает место ссылки в исходном YAML. Проходимость проверяется отдельно эталонными маршрутами.
2. **Установка.** Игрок открывает `.districtdeck` из Finder на Mac или из «Файлов» на iPad. Приложение проверяет архив и сохраняет кампанию вместе с иллюстрациями на устройстве. В основном YAML-файле автор задаёт постоянный `id`, название и версию. Библиотека узнаёт кампанию по `id`, в том числе после переименования архива.
3. **Замена.** Когда содержимое уже установленной кампании изменилось, игрок подтверждает замену для новых партий. Встроенный «Последний поезд» обновляется автоматически при запуске сборки с изменённым архивом. Начатые и завершённые прохождения ссылаются на исходную копию, даже если автор повторно использовал номер версии. Несколько партий могут ссылаться на одну копию.
4. **Продолжение.** Игра работает офлайн. Движок сохраняет состояние на входе в скрипт, включая шаг фазы, очередь, ресурсы, колоды, квесты, сюжет и состояние генератора при наличии случайности. Для встречи к этому моменту уже известны карта и персонаж. После прерывания тот же скрипт запускается с этих данных. При завершении встречи её эффекты, журнал, сброс карты и продвижение очереди попадают в одно сохранение. В завершённой партии доступны развязка и журнал.

**Ответ игрока.** Встречу ведёт `GameEngine`. При каждом `chooseOne` движок вызывает `await choose(варианты)` и ждёт номер ответа. В приложении функция возвращает выбор игрока, в тесте — заранее заданный выбор. Затем движок исполняет выбранную ветку и продолжает скрипт. [Состав вариантов ответа](ScriptLanguage.md#выбор-игрока)

**Результат встречи.** После успешного розыгрыша `GameEngine` возвращает изменения в порядке, в котором они произошли. У каждого изменения указана причина. Например, Иван тратит пять монет и получает посылку по выбранному ответу курьеру. Предмет в инвентаре выполняет условие квеста, а его завершение добавляет проводника в колоду вокзала. Журнал объединяет изменения в одну запись о встрече. Игровое поле показывает их по очереди в том же порядке.

**Предложение по исполнению скрипта.** Перед розыгрышем `GameEngine` создаёт рабочую копию изменяемого состояния этой партии. Команды и вызванные ими правила квестов работают с одной копией, включая будущие записи журнала и состояние генератора. Начать другой независимый розыгрыш в той же партии можно после завершения текущего. При успехе движок принимает результат целиком. При ошибке он отбрасывает копию и сообщает причину. После закрытия приложения партия возобновляется с сохранённого начала розыгрыша.

## Проверка архитектуры

«Без экрана» означает, что тест передаёт решение игрока в тот же движок, который будет вызывать SwiftUI. Например, из фиксированной позиции на площади тест выбирает обмен у курьера. Движок списывает у Ивана пять монет, выдаёт посылку, завершает квест, убирает оставшееся квестовое событие с почты и добавляет проводника в колоду вокзала. Правила обмена задаёт кампания. UI получает результат для отображения и анимации.

Для первого этапа согласованы три маршрута «Последнего поезда» с проверкой развязки и номера раунда через UI и без экрана, а также повторный розыгрыш прерванной встречи с курьером. На Mac и iPad отдельно проверяем, удобно ли двигать и приближать поле и виден ли путь фишки. Проверку обновления кампании можно воспроизвести, изменив реплику курьера при прежнем номере версии: старая партия должна показать исходный текст, новая — обновлённый. ## Открытые вопросы и предложения

- **Оформление карты.** На «Последнем поезде» пробуем готовую иллюстрацию с разметкой в `board/scene.yaml`. Сцена ссылается на клетки игрового графа по ID. Пригодность формата оценим по выбору клеток, подсветке и движению фишки на Mac и iPad. [Пример оформления поля](Campaigns/LastTrain.md#оформление-поля)
- **Библиотеки и тестовые инструменты.** Форматы YAML и ZIP выбраны. Конкретные библиотеки для них остаются деталями реализации. Для файлового ввода-вывода предложена Foundation, для пакетных тестов — Swift Testing, для проверок взаимодействия с UI — XCTest и XCUIAutomation. [Swift Testing](https://developer.apple.com/documentation/testing/) · [Тестирование интерфейса](https://developer.apple.com/documentation/xcode/testing)

На этапе прототипа существующие кампании можно обновлять вместе с движком. К поддержке прежних форматов вернёмся после появления играбельной версии и первых кампаний.
